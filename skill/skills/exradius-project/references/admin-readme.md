# The admin README

The config repository's `README.md` is written for the Exradius admin, who has never seen
the code. It is the only place that says what format each secret has and where to obtain
it: Exradius shows key names, never hints. Fill every `<...>`; drop rows and sections that
do not apply. No secret value ever goes into it, not even an example that looks real.

````markdown
# <Project name> on Exradius

Exradius config for <one line on the project>. Exradius reads `exradius.yaml` from this
repository on every run; changes take effect when they are pushed to `<branch>`.

| | |
|---|---|
| Config repository | <https URL of this repository> |
| Branch | `<branch>` |
| Config file | `exradius.yaml` (or `.exradius/exradius.yaml` in <code repository>) |
| Visibility | <private: Exradius needs a read credential for <host> (Settings, config repository access) / public: no credential needed> |
| Project slug | `<slug>` |
| Secret store | `<store>` |

## Add the project

1. <Private repositories only:> in Settings, add a credential for `<host>` that can read
   this repository (for GitHub: a fine-grained token with Contents: read on it).
2. Projects, Add: paste `<URL>`<, branch `<branch>` when not the default>.
3. Stores: create `<store>` and fill the keys below.
4. Open the project's Verify tab: every step should pass.

## Secret store `<store>`

| Key | Format | Where to get it | Used for |
|---|---|---|---|
| `GITHUB_TOKEN` | GitHub fine-grained personal access token, `github_pat_...` | github.com, Settings, Developer settings, Fine-grained tokens: resource owner `<owner>`, repositories <list>, permissions Contents: read and write, Pull requests: read and write, Metadata: read | cloning <and pushing> <repositories>; the `github` connection (pull requests) |
| `DB_PASSWORD` | any random string of letters and digits (no `@`, `:` or `/`: it goes into a URL) | generate one, for example `openssl rand -hex 24` | the `postgres` service's password and `DATABASE_URL`; it exists only inside runs |

The panel accepts a pasted `.env` block to fill several keys at once:

```
GITHUB_TOKEN=
DB_PASSWORD=
```

## What a run gets

- Workstation: <image, or "built from docker/workstation.Dockerfile: <languages and tool versions>">.
- Repositories: <name> (<branch>, push <allowed / not allowed>), ...
- Services: <name> (<image>), ...
- Setup: <one line per command and what it prepares>.
- Agents: `developer` (<what it does, whether it pushes and opens pull requests>), `scout`
  (investigates and reports, never changes code).
- Resources: `resources.memory` is `<N>g`: each run needs a cluster node with that much
  memory free (it waits as "waiting for cluster capacity" until one has), and the
  workstation is killed if it goes over it
  (<the heaviest step>)<; services: <name> `<N>m`, ...>. Disk: about <N> GB per run
  (<the biggest install>).
- Caches: <the package managers' stores, e.g. the pnpm store and uv's cache> are kept
  between runs in `<data dir>/caches/<slug>/` on the Exradius server (about <N> GB after
  the first run), shared by the project's runs, never cleaned by Exradius. The project
  page shows their size; delete that directory to clear them (the next run downloads
  everything again, nothing else is lost).

## Maintaining it

Edit `exradius.yaml` or the Dockerfile and push to `<branch>`. Before pushing, the
developers check it locally with the `exradius-project` Claude Code skill
(`skill/` in `musabeytekin/exradius`), whose `check.sh` runs the same steps as Verify with Docker.
````

## Formats and sources for common keys

| Key kind | Format | Where to get it |
|---|---|---|
| GitHub token (clone, push, `github` connection) | fine-grained `github_pat_...` (or classic `ghp_...` with `repo` scope) | GitHub Settings, Developer settings; scope it to the project's repositories; Contents read and write only when `push: true`; Pull requests read and write for the `github` connection |
| GitLab token | `glpat-...` with `read_repository` (and `write_repository` to push; `api` for the `gitlab` connection) | GitLab, User settings (or the project's Settings), Access tokens |
| Bitbucket / other hosts | `user:app-password` | the host's app password settings |
| Service passwords (Postgres, MySQL, RabbitMQ) | random letters and digits, URL-safe | generated by the admin; used only inside runs |
| Linear API key (`linear` connection) | `lin_api_...` | Linear, Settings, Security and access, Personal API keys |
| Sentry token (`sentry` connection) | `sntrys_...` user auth token | Sentry, User settings, Auth tokens |
| Slack (`slack` connection) | bot token `xoxb-...` and team id `T...` | api.slack.com, the app's OAuth and permissions page |
| Jira (`jira` connection) | Atlassian API token, plus the site URL and the account email | id.atlassian.com, Security, API tokens |
| Third-party API keys the tests need | as the provider issues them | name the provider's page; prefer a sandbox or test-mode key |

Values that are not secret (a test-only `SECRET_KEY`, user names, `NODE_ENV`, URLs of
services in the run) go into `env` as plain text, not into the store.
