# Governance, compliance and audit requirements for code changes in regulated enterprises, and what they imply for AI-agent-produced changes

Scope note for the writer: sources are a mix of primary texts (EU regulation reproductions, SEC rule release, GitHub docs, UK government guidance, Linux kernel docs, GDPR text) and secondary summaries (law-firm client alerts, compliance-tool control catalogues, vendor blogs). Each finding is tagged **[hard]** (legal/standard requirement), **[guidance]** (regulator or standards-body guidance, not binding), or **[practice]** (common enterprise or community practice). Where I could only reach a secondary source for a primary text, the finding says so. Date of research: 7 November 2026.

## 1. Change-management regimes: SOX ITGC, PCI DSS Requirement 6, ISO 27001 / SOC 2, ITIL 4, DORA, safety-critical software

### Takeaway
Every regime converges on the same five evidentiary facts per production change: an authorised request, a documented description and impact assessment, testing, approval by someone independent of the implementer, and a traceable, verified deployment with a fallback. DORA's RTS and PCI DSS v4.0.1 state these most explicitly as legal/standard text; SOX ITGC, ISO 27001 A.8.32 and SOC 2 CC8.1 are principle-based and leave the exact artefacts to the auditor; ITIL 4 is a practice framework that allows pre-authorised "standard" changes and automation as a change authority.

### Cited Findings

**SOX ITGC (US listed companies; principle-based, enforced through external audit)**
- [practice/audit expectation] Practitioner guidance states typical SOX change-management evidence is the change request, test results, pre-deployment approval, and proof that the person deploying was independent of the developer; auditors look for no emergency changes without documented approval and a complete trail of what changed and who changed it — [SafePaaS, key ITGC controls](https://www.safepaas.com/?p=11308); [SecurityScientist SOX ITGC change-management template](https://www.securityscientist.net/blog/sox-itgc-change-management-policy-template/)
- [practice] A typical SoD matrix lets the developer role write code but not approve or deploy it, with evidence retained as tickets, logs, approvals and test results; developers deploying their own code is treated as the central SoD risk — [SafePaaS, SOX separation of duties](https://www.safepaas.com/?p=9071); [Liquibase, SOX compliance for database change management](https://www.liquibase.com/resources/guides/sox-compliance-for-database-change-management-best-practices)
- [practice] Some auditors and tooling pull PR author, approver and merge/deploy actor from git and CI and flag records where the author appears among the approvers (self-approval test) — [HelpMeTest SOX compliance testing guide](https://helpmetest.com/blog/sox-compliance-testing-guide/) (vendor illustration, not an audit standard)
- [hard, retention] The SEC's rule implementing SOX §802 (Rule 2-06 of Regulation S-X) requires the auditor to retain records relevant to the audit "for a period of seven years after an accountant concludes an audit or review", including workpapers and records that "contain conclusions, opinions, analyses, or financial data related to the audit or review", whether or not they support the final conclusion — [SEC final rule, Retention of Records Relevant to Audits and Reviews (2003)](https://www.sec.gov/rules-regulations/2003/01/retention-records-relevant-audits-reviews). Note: the seven-year rule binds the auditor's workpapers; the issuer's own change-record retention is set by its policy and the auditor's needs (see Gaps).
- No source found cites PCAOB AS 2201 or SEC text that prescribes specific change-management artefacts; the specificity above comes from audit-firm practice (the first search returned only practitioner/vendor material) — [search summary](https://nhimg.org/articles/sox-itgc-governance-is-the-real-audit-battleground/)

**PCI DSS v4.0.1 (contractual standard for entities handling cardholder data; v4.0 retired 31 Dec 2024)**
- [hard] 6.2.3: "Bespoke and custom software is reviewed prior to being released into production or to customers" to ensure code follows secure coding guidelines, looks for existing and emerging vulnerabilities, and that corrections are implemented prior to release — [Cloudaware PCI DSS v4.0.1 6.2.3](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/06/02/03)
- [hard] 6.2.3.1: if manual code reviews are performed, "code changes are reviewed by individuals other than the originating code author", by individuals knowledgeable about code-review techniques and secure coding, and are "reviewed and approved by management prior to release" — [Cloudaware PCI DSS v4.0.1 6.2.3](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/06/02/03); secondary confirmation that automated SAST can satisfy the review requirement if it covers the 6.2.4 vulnerability classes — [Presencis PCI DSS developer guide](https://cdn.presencis.com/regulations/pci-dss/guide/developer)
- [hard] 6.5.1: "Changes to all system components in the production environment are made according to established procedures"; 6.5.2: after a significant change, confirm all applicable PCI DSS requirements are in place and update documentation; 6.5.3: "Pre-production environments are separated from production environments" with access controls enforcing the separation; 6.5.4: roles and functions are separated between production and pre-production so only reviewed and approved changes are deployed; 6.5.5: "Live PANs are not used in pre-production environments" except where the pre-production environment is inside the CDE and fully protected; 6.5.6: "Test data and test accounts are removed from system components before the system goes into production" — [Cloudaware PCI DSS v4.0.1 6.5](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/06/05)
- [hard, retention] 10.5.1: retain audit log history for at least 12 months, with at least the most recent three months immediately available for analysis — [WithPCI 10.5.1](https://withpci.pages.dev/requirements/10/10.5/10.5.1); [Cloudaware 10.5.1](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/10/05/01)
- Version/numbering caveat: v3.2.1 numbered change control 6.4 and code review 6.3.2; v4.x renumbered to 6.5 and 6.2.3 — [search summary with multiple catalogues](https://ce.prod.cloudaware.com/frameworks/pci-dss-v3.2.1/06/04/05)

**ISO/IEC 27001:2022 Annex A 8.32 and SOC 2 CC8.1**
- [hard, if certified; wording is principle-level] A.8.32 Change management requires that changes to information processing facilities and systems be subject to change-management procedures; the purpose is that changes are controlled and authorised; the control text itself does not prescribe artefacts — [Advisera, control 8.32](https://advisera.com/iso27001/control-8-32-change-management/); [ISMS.online A.8.32](https://www.isms.online/iso-27001/annex-a-2022/8-32-change-management-2022/). Sources disagree on whether the control reads "should" or "shall" — [Hightable](https://hightable.io/iso27001-annex-a-8-32-change-management) vs [AuditFront](https://auditfront.pages.dev/frameworks/iso-27001/technological/a-8-32).
- [practice] Typical A.8.32 audit evidence: change-request logs from Jira/ServiceNow showing submission, approval and implementation status; an approved policy defining Standard, Normal and Emergency categories — [iso-docs.com](https://iso-docs.com/blogs/iso-27001-controls-catalog/control-of-production-changes-iso-27001); [Hightable audit checklist](https://hightable.io/iso-27001-annex-a-8-32-audit-checklist)
- [hard, if SOC 2 reported] SOC 2 CC8.1 requires that changes to infrastructure, data, software and procedures are authorised, designed, developed, configured, documented, tested, approved and implemented; practitioners say CI/CD artefacts (PR approvals, automated test results, immutable deployment logs) can serve as the evidence — [AuditFront CC8.1](https://auditfront.pages.dev/frameworks/soc-2/common-criteria/cc8-1); [SecurityScientist community answer](https://answers.securityscientist.net/q/26216/what-does-soc-2-cc8-actually-require-for-change-management) (community answer, not AICPA)
- [practice] A.8.32 and CC8.1 are commonly mapped to each other so one evidence set serves both — [AuditFront A.8.32](https://auditfront.pages.dev/frameworks/iso-27001/technological/a-8-32)

**ITIL 4 change enablement (practice framework, not a requirement)**
- [practice] ITIL 4 defines three change types: standard (pre-authorised, low risk, bypass CAB), normal (assessed and authorised per change), emergency (expedited; may be reviewed by an Emergency CAB; testing may be reduced but "never skipped without acceptance of the added risk") — [ITSM.tools, change enablement](https://itsm.tools/change-enablement/); [Faddom, standard vs normal vs emergency](https://faddom.com/itil-change-management-types-standard-vs-normal-vs-emergency/); [InvGate, emergency change](https://blog.invgate.com/emergency-change-control-process)
- [practice] ITIL 4 replaces "everything through the CAB" with a "change authority" that can be a person, a board, or an automated rule, set per change type — [Open Exam Prep ITIL 4 Foundation notes](https://open-exam-prep.com/study-guides/itil-4-foundation/core-practices-i/change-enablement); [ServiceNow change types](https://www.servicenow.com/docs/r/it-service-management/change-management/change-types.html)

**EU DORA (Regulation 2022/2554, applicable 17 Jan 2025) and RTS 2024/1774 Article 17**
- [hard] DORA Art. 9(4)(e) requires financial entities to have documented policies, procedures and controls for ICT change management so that changes to ICT systems are "recorded, tested, assessed, approved, implemented and verified in a controlled manner" — [Springlex DORA Article 9](https://www.springlex.eu/en/packages/dora/dora-regulation/article-9/); [iso-docs Article 9 reproduction](https://iso-docs.com/blogs/dora-articles/article-9-digital-operational-resilience-act-dora-protection-and-prevention)
- [hard] RTS 2024/1774 Art. 17(1) requires the change-management procedure to cover all changes to software, hardware, firmware, systems or security parameters and to include: (a) verification that ICT security requirements are met; (b) "mechanisms ensuring the independence of the functions approving changes from the functions requesting and implementing them"; (c) roles and responsibilities for specifying, planning, testing and finalising changes with quality assurance; (d) documentation and communication of purpose, scope, timeline and expected outcomes; (e) fall-back procedures for aborting or recovering from failed changes; (f) procedures, protocols and tools for emergency changes with adequate safeguards; (g) documenting, re-evaluating, assessing and approving emergency changes after implementation, including workarounds and patches; (h) identifying the impact of a change on existing security measures — [Springlex RTS 2024/1774 Article 17](https://www.springlex.eu/en/packages/dora/rts-rmf-regulation/article-17/); [Advisera Article 17 commentary](https://advisera.com/cdr-2024-1774/ict-change-management/)
- [hard] Art. 17(2): CCPs and CSDs must subject ICT systems to "stringent testing by simulating stressed conditions" after significant changes — same source.
- Logging is handled separately in RTS Article 12, not Article 17 — [Springlex Article 17](https://www.springlex.eu/en/packages/dora/rts-rmf-regulation/article-17/)
- [guidance] EBA Guidelines on ICT and security risk management (EBA/GL/2019/04), section 3.6 "ICT project and change management", predate DORA and require defined roles, responsibilities and accountabilities for changes; a third-party control mapping ties "Access Restrictions for Change" to sections 3.4.4 and 3.6.3 — [EBA final guidelines PDF](https://www.eba.europa.eu/sites/default/documents/files/documents/10180/2522896/32a28233-12f5-49c8-9bb5-f8744ccb4e92/Final%20Guidelines%20on%20ICT%20and%20security%20risk%20management.pdf?retry=1); [OpenSecurityArchitecture EBA mapping](https://opensecurityarchitecture.org/frameworks/eba-ict/controls). Whether the EBA text explicitly forbids developer production access could not be confirmed from the retrieved pages.

**Aviation and safety-critical software**
- [guidance] EASA published an AI Concept Paper (2024) covering Level 1 and 2 machine-learning applications, framed against EU AI Act Chapter III; the MLEAP project produced a final report as a complement to established development standards — [LDRA, AI/ML for safety-critical applications](https://ldra.com/artificial-intelligence-machine-learning-for-safety-critical-applications/)
- [academic] A 2024 review applying the EASA concept paper found ARP4754B, ARP4761A and DO-178C "not fully applicable" to ML components because behaviour is specified by data and white-box verification is limited — [Frontiers in Aerospace Engineering 2024](https://www.frontiersin.org/journals/aerospace-engineering/articles/10.3389/fpace.2024.1475139/pdf); [arXiv 2409.08666](https://arxiv.org/html/2409.08666v1)
- [opinion] For conventional (non-ML) airborne code written with AI help, a vendor commentary states AI-generated code is subject to the same DO-178C scrutiny as human code: traceability to requirements, coding-standard compliance, independent review, deterministic testing; AI should be an assistant, not an autonomous author of certified code — [ePlane AI](https://www.eplaneai.com/news/applying-ai-in-aerospace-software-development-under-do-178c-standards) (vendor blog)

### Inferences
- The lowest common denominator across SOX, PCI, ISO, SOC 2 and DORA is a per-change record with: request/ticket reference, change description and rationale, security-impact assessment, test evidence, independent approval, deployment record, and back-out plan. An agent harness that cannot emit these per task will fail the "operating effectiveness" sample test regardless of how good the code is.
- What an agent harness must produce: (1) immutable run record binding task id → config commit → repository + base commit → branch and head commit → result (the "request" and "description"); (2) the agent's test output and the CI results as attached evidence ("tested"); (3) nothing that acts as approval or deployment — those must be performed by humans/pipelines outside the harness so that independence (DORA 17(1)(b), PCI 6.2.3.1, SOX SoD) is preserved; (4) a back-out path, which for code is the unmerged branch itself; (5) emergency-change handling must remain a human process — an agent should not be given a path that bypasses review.
- ITIL 4's "standard change" with an automated change authority is the only framework that legitimately permits a fully automated path to production; even then the change type must be pre-assessed and pre-authorised, which argues for a per-project allowlist of change classes an agent may complete end-to-end.
- Retention: 12 months hot (PCI 10.5.1) is a floor for the harness's own event/transcript store; audit workpaper logic (SOX 7 years) means exported evidence must survive far longer than the harness itself, so events should be exportable in a stable format.

### Gaps
- Exact PCI DSS v4.0.1 6.5.1 bullet text (reason/description, security impact, approval by authorised parties, testing, back-out) could not be fetched from a reproducible page (catalogue pages showed titles only, one fetch rate-limited). The bullets are consistently described in secondary sources but should be confirmed in the PCI SSC document.
- No primary PCAOB/SEC text prescribing SOX change-management artefacts was found; the evidence list is audit-firm practice. No Deloitte/PwC/KPMG/EY document specifically on SOX ITGC for AI-generated code was found (see section 5).
- Issuer-side record-retention periods for change tickets under SOX are set by company policy; no authoritative number found beyond the auditor's seven-year workpaper rule.
- No EASA/RTCA position specific to AI-generated conventional code under DO-178C was found.

## 2. Segregation of duties: author vs approver vs deployer, enforcement mechanisms, and the bot author

### Takeaway
PCI DSS 6.2.3.1 and DORA RTS 17(1)(b) make author/approver independence a standard or legal requirement; SOX audits treat it as the core ITGC SoD test. Enterprises enforce it with branch protection (required reviews, no self-approval, dismiss stale reviews, approval of most recent push, CODEOWNERS, status checks, no admin bypass). GitHub's model already prevents an author's approval from counting; a bot author therefore needs a distinct human approver, and the literature is clear that AI agents must not self-certify (no Signed-off-by from agents, humans "fully responsible").

### Cited Findings
- [hard] PCI DSS 6.2.3.1: manual code reviews by "individuals other than the originating code author" and "reviewed and approved by management prior to release" — [Cloudaware 6.2.3](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/06/02/03)
- [hard] DORA RTS Art. 17(1)(b): independence of approving functions from requesting and implementing functions — [Springlex RTS Article 17](https://www.springlex.eu/en/packages/dora/rts-rmf-regulation/article-17/)
- [hard] PCI DSS 6.5.4: roles and functions separated between production and pre-production so only reviewed and approved changes are deployed — [Cloudaware 6.5](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/06/05)
- [practice, mechanism] GitHub branch protection: changes reach a protected branch only through a PR "approved by the required number of reviewers with write permissions"; "Dismiss stale pull request approvals when new commits are pushed" invalidates approvals when the diff changes; "Require approval of the most recent reviewable push" means the latest push "must be approved by someone other than the person who pushed it"; "Require review from Code Owners" forces approval from the owner of touched paths; required status checks can be restricted to a specific GitHub App; admins bypass by default unless "Do not allow bypassing the above settings" is set; "Require signed commits" means contributors and bots can only push verified-signed commits — [GitHub docs, About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- [practice] GitHub does not let a PR author's own approval count, and a code owner who authored the change cannot satisfy their own owner-review requirement; users have requested an exemption since 2017; one commenter reports running two separate bot accounts so one opens the PR and another approves — [GitHub community discussion 131419](https://github.com/orgs/community/discussions/131419); [discussion 14866](https://www.Github.com/orgs/community/discussions/14866). (The two-bot workaround defeats the control's intent and would not pass an SoD test; this is my inference.)
- [practice] UK Government guidance for AI coding assistants: "The main branch and resulting artefacts need to be protected from unchecked modifications"; merges to main need human peer review combined with branch protection; "You should only commit code changes that you understand"; "As a developer, you are fully responsible for the code you produce, whether this is AI assisted or not"; if a production service is "developed, maintained and deployed from a single environment", AI coding assistants may introduce unacceptable risk — [GOV.UK AI Insights: AI coding assistants for developers in HMG (updated 3 Aug 2026)](https://www.gov.uk/government/publications/ai-insights/ai-insights-ai-coding-assistants-for-developers-in-hmg-html)
- [practice, open source] Linux kernel: "AI agents MUST NOT add Signed-off-by tags. Only humans can legally certify the Developer Certificate of Origin (DCO)"; the human submitter must review all AI-generated code, ensure licensing compliance, add their own Signed-off-by and take "full responsibility for the contribution"; assistants must "say so explicitly" if a fix could not be built or tested — [kernel.org Documentation/process/coding-assistants](https://www.kernel.org/doc/html/latest/process/coding-assistants.html)
- [practice, US state government] Maryland's AI governance card for coding assistants says developers remain 100% responsible for the final versions of any outputs AI coding assistants produce and permits only enterprise/government versions of the tools — [Maryland DoIT governance card](https://doit.maryland.gov/policies/ai/Pages/AI-powered-coding-assistants.aspx) (page returned 403 on direct fetch; wording from search summary)
- [guidance] NY DFS industry letter of 21 May 2026 (under 23 NYCRR Part 500; creates no new legal requirement) says secure-programming measures "may include additional testing and validation procedures, including human oversight, for AI-generated code prior to deployment in production environments" — [Sidley Data Matters, 28 May 2026](https://datamatters.sidley.com/2026/05/28/new-york-department-of-financial-services-issues-coordinated-guidance-on-frontier-ai-cybersecurity-risks/); [Willkie Compliance Concourse](https://complianceconcourse.willkie.com/articles/nydfs-issues-two-industry-letters-addressing-heightened-cybersecurity-risks-from-frontier-ai-models-and-guidance-for-heightened-threat-environments/)
- [practice, vendor] Non-human-identity guidance: separate code-review automation from release automation; a bot that opens PRs or merges code should not inherit broad permissions "just because it is part of the pipeline" — [NHI Management Group FAQ](https://nhimg.org/faq/how-should-teams-govern-github-access-across-human-and-non-human-identities/)

### Inferences
- For a bot author, SoD is satisfied only if (a) the bot identity is distinct and attributable (own GitHub App / service identity, not a human's token), (b) the bot has no permission to approve, merge or deploy, and (c) a human with write permission approves and the approval is of the most recent push. If the agent pushes new commits after review, "dismiss stale approvals" re-opens the gate — the harness should expect this and not treat an approved-then-updated PR as done.
- The harness must therefore record who the human requester was (the ticket), that the agent authored, and must deliberately lack the credentials to merge or deploy. The Exradius principle "the worker never commits or pushes on behalf of the agent and never merges" maps directly to this; the agent pushing a branch is "implementing", not "approving".
- Auditors will ask for a sample of changes and check author ≠ approver ≠ deployer. If the agent's commits carry a human's name (e.g. a personal token), the trail collapses the author and the approver into one identity. Commits should be attributed to the agent identity, with the human requester recorded in the ticket/trailer, not as author.
- Agent-authored changes are best classed as ITIL "normal" changes by default; only pre-assessed classes (dependency bumps, docs) could become "standard" changes with automated authority, and that classification itself needs documented approval.

### Gaps
- No regulator text specifically addresses whether a bot may be the "requester" or "implementer" for DORA 17(1)(b) purposes; the independence wording is about functions, so the analysis above is inference.
- No audit-firm publication found that states how a Big Four auditor samples/treats bot-authored PRs under SOX.

## 3. Traceability: ticket → branch → commit → PR → deployment; signed commits and provenance; audit-log retention

### Takeaway
Traceability is a hard requirement in DORA (changes "recorded… verified") and PCI (documented change with reason, approval) and an audit expectation under SOX; the mechanics (issue key in branch and commit, PR linking, Smart Commits, trailers) are common practice. Signed commits and SLSA provenance are not legally required by any regime found but are increasingly the way enterprises prove "who/what produced this artefact". Platform audit logs are short-lived (GitHub: 180 days, Git events 7 days), so evidence must be exported to the enterprise's own store to meet 12-month (PCI) and multi-year (SOX) horizons.

### Cited Findings
- [hard] DORA Art. 9(4)(e): changes "recorded, tested, assessed, approved, implemented and verified in a controlled manner" — [Springlex DORA Article 9](https://www.springlex.eu/en/packages/dora/dora-regulation/article-9/)
- [hard] RTS 17(1)(d): documentation of purpose, scope, implementation timeline and expected outcomes of each change — [Springlex RTS Article 17](https://www.springlex.eu/en/packages/dora/rts-rmf-regulation/article-17/)
- [practice] Jira Smart Commits: syntax `<ignored text> <ISSUE_KEY> <ignored text> #<COMMAND>`; issue keys are two+ uppercase letters, hyphen, number (e.g. JRA-123); `#comment`, `#time`, `#transition`; the committer's email must match exactly one Jira user with permission or the Smart Commit fails (the git commit still succeeds); linked development information appears in the work item's Development panel; PR titles are copied into merge commit messages — [Atlassian, Process issues with Smart Commits](https://support.atlassian.com/jira-software-cloud/docs/process-issues-with-smart-commits/)
- [practice] GitHub "Require signed commits": only signed and verified commits may be pushed by contributors and bots; unsigned head-branch commits can block a squash merge even though GitHub signs the squash commit — [GitHub docs, About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- [practice, standard] SLSA Build track: L1 "Provenance exists" describing how the artifact was built (build platform, process, top-level inputs), distributed to consumers; L2 builds on hosted infrastructure with provenance tied to it by a digital signature; L3 isolates runs from each other and keeps signing material away from user-defined build steps. SLSA 1.0 page is marked retired; v1.2 is current — [SLSA v1.0 levels](https://slsa.dev/spec/v1.0/levels)
- [practice, open source] Linux kernel, Fedora, LLVM, OpenTelemetry, OpenInfra and Rocky Linux have reportedly converged on an `Assisted-by:` commit trailer for AI assistance; the kernel "deliberately stopped short of CI enforcement"; QEMU and Gentoo (council vote April 2024) and NetBSD ban AI-generated contributions, and QEMU has a pending proposal for an `AI-used-for:` trailer exception — [DEV Community, AI attribution governance](https://dev.to/shenxianpeng/ai-attribution-governance-enforcing-ai-disclosure-policies-at-the-ci-level-492a); [Linuxiac on QEMU](https://linuxiac.com/qemu-may-relax-its-ban-on-ai-generated-contributions/); [Tom's Hardware on the kernel decision](https://www.tomshardware.com/software/linux/linux-lays-down-the-law-on-ai-generated-code-yes-to-copilot-no-to-ai-slop-and-humans-take-the-fall-for-mistakes-after-months-of-fierce-debate-torvalds-and-maintainers-come-to-an-agreement) (all secondary; the kernel's tool-generated-content page returned 404)
- [practice, retention] GitHub Enterprise audit log covers the last 180 days; "The audit log retains Git events for seven days"; Git events initiated via the web UI or REST/GraphQL APIs (e.g. a PR merged in the browser) are not included in Git-event exports; audit-log streaming to an external system covers audit and Git events — [GitHub docs, Exporting audit log activity for your enterprise](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/exporting-audit-log-activity-for-your-enterprise)
- [hard, retention] PCI DSS 10.5.1: 12 months, 3 months immediately available — [WithPCI 10.5.1](https://withpci.pages.dev/requirements/10/10.5/10.5.1)
- [hard, retention] SEC Rule 2-06: seven years from conclusion of the audit for records relevant to the audit — [SEC final rule 2003](https://www.sec.gov/rules-regulations/2003/01/retention-records-relevant-audits-reviews)
- [practice] Vendor description of what auditors ask for with AI tooling: records linking prompts, generated code, policy checks and developer actions — [Legit Security executive brief](https://www.legitsecurity.com/blog/executive-brief-questions-ai-is-creating-that-security-cant-answer-today); [Checkmarx, AI coding assistants with audit trails](https://checkmarx.com/learn/ai-security/ai-coding-assistants-with-audit-trails-and-security-governance-top-8-options.md) (vendor)
- [practice] A Swiss banking engineering firm proposes five evidence items for auditable AI-generated code: an inventory of AI tools, attribution of AI-assisted changes, documented human review gates, visibility into data sent to external models, and reproducibility of past approvals; it frames the question as "whether every production change can be traced and defended" and recommends treating AI coding governance as part of SDLC and supplier control, not a standalone AI policy — [CREATEQ via transparencywins.info, 29 Aug 2026](https://transparencywins.info/insight/createq-making-ai-generated-code-auditable-in-banking)

### Inferences
- Harness requirements for traceability: the task id must appear in the branch name and in every commit message (the ticket-key convention is what Jira/GitHub/GitLab integrations parse); commits should carry machine-readable trailers (task id, agent identity, config commit, run id, and an `Assisted-by:`-style disclosure) so the trail survives squash merges that drop PR metadata; the harness's own event store should link run id ↔ task id ↔ repository ↔ base commit ↔ head commit ↔ result, and be exportable because the platform audit log will not retain it.
- Commit signing: if the organisation requires signed commits, an agent's pushes will be rejected unless the agent identity has a signing key; the key must be the agent's own (not a human's) to keep attribution honest. Sigstore keyless signing (OIDC identity, short-lived certificates, transparency log) is the natural fit but could not be verified from primary docs in this run (see Gaps).
- Reproducibility (CREATEQ item 5): record the model/provider and version, the system prompt/rules version, the config-repo commit and the tool set available to the agent per run, otherwise a past approval cannot be re-examined.
- Audit log retention: the harness must assume GitHub keeps Git events for only 7 days; the 12-month and 7-year horizons must be met by the harness's own retained events/transcripts or by an enterprise SIEM fed via streaming.

### Gaps
- Sigstore gitsign documentation (two URLs) returned 404; no primary description of keyless commit signing captured.
- The kernel's `Assisted-by:` trailer format/example page returned 404; wording is from secondary reports.
- No standard found that mandates signed commits or SLSA levels for regulated enterprises; these remain practice/procurement requirements (e.g. US federal SSDF attestations were not researched here).
- No authoritative ISO 27001 or SOC 2 log-retention period exists (both are policy-defined); no source gives a DORA-mandated retention period for change records.

## 4. Production data and personal data during development; what may enter AI tools; transcripts, prompts and logs; retention and erasure

### Takeaway
GDPR makes data minimisation, storage limitation and demonstrable accountability binding on any development process that touches personal data; PCI DSS forbids live PANs in pre-production and requires test data removal before go-live; pseudonymised/masked data is still personal data under GDPR. Government and regulator guidance for AI coding assistants is unanimous that production data and secrets must not enter the tool, that enterprise contracts (no training on prompts) are expected, and that transcripts/prompts are records subject to retention and erasure obligations — which conflict with audit retention and must be reconciled by design (minimise what is captured, placeholder secrets, redact PII, keep what audit needs under the legal-obligation exception).

### Cited Findings
- [hard] GDPR Art. 5(1)(c): personal data must be "adequate, relevant and limited to what is necessary in relation to the purposes for which they are processed"; 5(1)(e): "kept in a form which permits identification of data subjects for no longer than is necessary"; 5(1)(f): "processed in a manner that ensures appropriate security of the personal data"; 5(2): "The controller shall be responsible for, and be able to demonstrate compliance with, paragraph 1" — [gdpr-info.eu Article 5](https://gdpr-info.eu/art-5-gdpr/)
- [hard] GDPR Art. 17: erasure "without undue delay" where data are no longer necessary, consent withdrawn, processing unlawful, etc.; exceptions where processing is necessary "for compliance with a legal obligation" (17(3)(b)) or "for the establishment, exercise or defence of legal claims" (17(3)(e)) — [gdpr-info.eu Article 17](https://gdpr-info.eu/art-17-gdpr/)
- [hard] PCI DSS 6.5.5: live PANs not used in pre-production environments (unless inside the CDE and fully protected); 6.5.6: test data and test accounts removed before production; 6.5.3: pre-production separated from production by access controls — [Cloudaware 6.5](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/06/05)
- [practice/legal analysis] Masking that keeps a lookup key is pseudonymisation, not anonymisation, and pseudonymised data remain personal data under GDPR; a tiered approach uses fully synthetic data in dev, masked subsets in QA, and de-identified production samples only when parity is essential; vendor claims that synthetic data is automatically outside GDPR are overstated — [Ranger, synthetic vs masked data](https://www.ranger.net/post/synthetic-data-vs-masked-data-testing); [AccountableHQ, production data in healthcare testing](https://www.accountablehq.com/post/using-production-data-in-healthcare-testing-compliance-privacy-and-best-practices) (vendor sources; no EDPB/ICO/HHS primary text retrieved)
- [guidance, government] UK Government AI coding assistant guidance: "You should never handle sensitive production data or secrets in development environments"; secrets in the workspace may be uploaded to the inference layer; "Production secrets should not be regularly shared with an AICA provider"; business/enterprise contracts are strongly recommended because free or personal-licence tools may record prompts and responses for training; confirm beta features are not excluded from data-collection terms; monitor tool and model versions — [GOV.UK AI Insights: AI coding assistants in HMG](https://www.gov.uk/government/publications/ai-insights/ai-insights-ai-coding-assistants-for-developers-in-hmg-html)
- [guidance, government] Maryland permits only enterprise or government versions of coding assistants — [Maryland DoIT](https://doit.maryland.gov/policies/ai/Pages/AI-powered-coding-assistants.aspx) (via search summary)
- [guidance, regulator] HMRC guidance for software developers using generative AI (28 Jan 2026): products must comply with UK GDPR, embed privacy by design and SSDLC practices; "strong human oversight and control built in at appropriate stages"; expects "continuous monitoring, version control and timely updating" of code and data sources — [GOV.UK, Guidelines for using generative AI if you're a software developer](https://www.gov.uk/guidance/guidelines-for-using-generative-artificial-intelligence-if-youre-a-software-developer)
- [practice] Agent-memory/transcript governance: redact PII before it reaches the model and before logs are written; keep retention to the shortest period serving the purpose; automatic deletion is more reliable than manual; make sure an erasure request actually removes stored memory entries; a provider's 30-day retention window does not remove breach risk during the window — [Daniel Vaughan, Agent memory governance](https://codex.danielvaughan.com/2026/04/16/agent-memory-governance-gdpr-retention-enterprise-policies/); [TheNeuralBase, secret leakage in prompts](https://theneuralbase.com/llm-for-coding/learn/advanced/secret-leakage-in-prompts/) (practitioner blogs)
- [practice, banking] Evidence item "visibility into what data leaves the bank for external models" — [CREATEQ via transparencywins.info](https://transparencywins.info/insight/createq-making-ai-generated-code-auditable-in-banking)
- [guidance] NY DFS 21 May 2026 letters also call for stronger logging and alerting and mapping of third-party dependencies, applying to model providers as third parties — [Sidley](https://datamatters.sidley.com/2026/05/28/new-york-department-of-financial-services-issues-coordinated-guidance-on-frontier-ai-cybersecurity-risks/)

### Inferences
- Transcripts, prompts, tool outputs and attachments produced by an agent run are both (a) audit evidence that must be retained (12 months hot under PCI if in scope; years for SOX-relevant systems) and (b) potential personal-data records subject to minimisation and erasure. The reconciliation that regulators accept is: minimise by design (secrets as `$NAME` placeholders, no production data mounted into the run, PII redaction on ingest), classify transcripts as change-control records with a documented retention schedule, and rely on Art. 17(3)(b)/(e) only for the audit-necessary subset.
- A harness must be able to state, per run, exactly which external endpoints received data (the model provider, MCP connections) and under which contract (enterprise/no-training). This is the "data sent to external models" evidence item and the UK/Maryland enterprise-licence rule.
- Service containers started for a task should be seeded with synthetic or masked data only; the harness should make "production credentials in a run" a configuration error, not a warning, for projects flagged as PCI/GDPR scoped.
- An erasure capability per run or per data subject (delete transcript/attachments while keeping the non-personal event skeleton) is needed; GDPR does not fix a period, so the retention schedule must be explicit and enforced automatically.

### Gaps
- No primary EDPB/ICO/HHS guidance on pseudonymisation or de-identification for test data retrieved (vendor sources only).
- Current retention and training-use terms of specific coding-agent vendors (Anthropic, GitHub Copilot, Cursor) were not researched; the UK guidance's claim about free-tier training is generic.
- No regulator statement found that explicitly classifies AI coding-assistant transcripts as change-control records; that is inference.

## 5. Policies and guidance on AI-generated code and AI agents in regulated companies, 2024–2026

### Takeaway
As of late 2026 no regulator imposes a code-specific legal rule for AI-generated code; the binding layer is existing change-control, SDLC and third-party-risk law (DORA, Part 500, GDPR, PCI). Guidance has converged on: the human submitter/deployer is accountable; human review before production; attribution/disclosure of AI assistance; inventory of tools and models; enterprise licences and IP indemnity conditions; agents need their own identities, prohibited-action lists, approval thresholds and audit trails (FSB, OWASP ASI03). The EU AI Act touches internal coding assistants mainly through the Article 4 AI-literacy duty (applies from 2 Feb 2025); US bank model-risk guidance SR 26-2 (April 2026) explicitly excludes generative and agentic AI from its scope.

### Inferences
- The consistent accountability model is: the AI is a tool; the human who requests, reviews and merges is accountable; the agent must never hold a role that certifies (sign-off, approval, deploy). A harness should make the human requester explicit in the task record and make the agent's output a proposal (branch/PR/patch), never a merge.
- Disclosure: enterprises will increasingly require machine-readable AI attribution on commits/PRs (the `Assisted-by:`/`Co-authored-by:` convention, tool inventory). The harness should stamp agent identity, model/provider id and run id into commit trailers and PR body, and keep the Claude Code `includeCoAuthoredBy` decision as a project-level, documented choice because some organisations want the trailer and some forbid AI co-author lines.
- Reproducibility of past approvals requires versioning of: the model id, the system prompt/operating rules, the project config commit, the connection/tool set, and the runtime image digest — all should be in the run record.
- Licensing/IP: regulated companies expect enterprise licences with indemnity and public-code filters; a self-hosted harness should at least record which provider/plan was used per run and allow a project to require a provider marked as enterprise/no-training.
- OWASP ASI03/ASI04/ASI05 translate into harness controls: per-run scoped credentials that the agent cannot see in clear text, an allowlist of MCP connections per project, and sandboxed execution with no path to production networks.
- EU AI Act impact for an internal coding agent is modest today (Art. 4 literacy for staff who use/approve it, GPAI obligations fall on the model provider); high-risk obligations apply only if the agent is used in an Annex III context, which code changes to internal systems are not.

### Gaps
- Primary texts of the NY DFS letters, the FSB final report, SR 26-2, and the COSO GenAI guidance were not readable; all content is via law-firm/press summaries.
- No published, named bank engineering policy on AI-generated code was found for 2025; the Swiss consultancy framework is the closest. No telecom or healthcare company policy was found.
- No audit-firm (Big Four) methodology for testing AI-authored changes under SOX was found.
- The OWASP agentic Top 10 mitigations (official text) were not retrieved; only risk names and vendor glosses.

## 6. Access control and least privilege for bots and service accounts: scoped tokens, per-repository credentials, approval of bot access, rotation

### Takeaway
No regulator prescribes bot-credential mechanics, but PCI (separation of environments and roles), DORA RTS (independence of functions; logging in Art. 12), OWASP ASI03 and the FSB draft (individual identifiers for agents, access limits) all push toward: a distinct, organisation-owned machine identity per agent, repository-scoped short-lived credentials, no production credentials in the agent's reach, registered ownership and periodic review, and attribution of every action to that identity. GitHub Apps with installation tokens are the platform-native pattern; shared bot accounts and classic PATs are the anti-pattern.

### Cited Findings
- [practice, platform] GitHub fine-grained PATs restrict access to selected repositories and granular permissions; classic PATs are all-or-nothing; organisation admins can review, approve or deny fine-grained token creation and enforce maximum lifetimes; GitHub recommends GitHub Apps or Actions for long-term automation — [DevClass on fine-grained PATs](https://devclass.com/2022/10/19/github-fixes-over-broad-token-permissions-with-fine-grained-personal-access-tokens-and-controversial-enforced-expiration); [Fast.io PAT vs fine-grained](https://www.fast.io/resources/github-pat-vs-fine-grained-token-copilot.md) (secondary)
- [practice, platform] A GitHub App acts as its own identity (e.g. `my-app[bot]`), can be installed on selected repositories only, and issues short-lived installation tokens (reported as 60 minutes; verify in GitHub docs); rotation becomes rotation of the app's private key rather than of per-user tokens — [DEV Community, GitHub Apps vs PATs](https://dev.to/patelaryan66/why-github-apps-are-better-than-personal-access-tokens-for-automation-1lg9); [Open Exam Prep least-privilege notes](https://open-exam-prep.com/study-guides/github-ai-developer/guardrails-accountability/least-privilege-policy); [Medium, PAT vs GitHub Apps](https://michaelkasingye.medium.com/github-authentication-personal-access-tokens-vs-github-apps-0f8fba446fbd) (all secondary)
- [practice] Machine/bot accounts are ordinary accounts and inherit every repository their team can reach; use a shared mailbox for the account so access survives staff changes — [Imperial College service accounts guidance](https://imperialcollegelondon.github.io/docs/security/service_accounts)
- [practice] GitLab's machine-identity design proposes standardising on service accounts and bars them from creating top-level namespaces so groups stay under explicit human ownership (status: proposed) — [GitLab handbook, Standardized machine identity](https://handbook.gitlab.com/handbook/engineering/architecture/design-documents/machine_identity)
- [practice] Non-human identities (GitHub Apps, service accounts, PATs, CI identities) should be registered, owned and reviewed as assets with purpose, scope and expiration; task-scoped access for bots that open PRs; separate review automation from release automation; "Log every non-human action with enough context to reconstruct intent"; no universal standard for GitHub bot governance exists yet — [NHI Management Group](https://nhimg.org/faq/how-should-teams-govern-github-access-across-human-and-non-human-identities/) (vendor)
- [guidance] FSB June 2026 draft: assign and document individual identifiers for AI agents; limit access to external environments; restrict direct access to payment systems; audit trails of agent transactions — [TechInformed](https://techinformed.com/fsb-calls-for-tighter-controls-on-agentic-ai-in-finance/)
- [guidance] OWASP ASI03 Identity and Privilege Abuse: agents inheriting, caching or passing along credentials; manage agent credentials as strictly as human ones; track delegation paths — [SecureFlag guide](https://blog.secureflag.com/2026/01/09/guide-owasp-top-ten-agentic-ai/)
- [hard] PCI DSS 6.5.3/6.5.4: production and pre-production separated with access controls and separated roles — [Cloudaware 6.5](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/06/05)
- [guidance, government] UK: "strict separation and audit of production secret access"; secrets in the workspace may be uploaded to the model — [GOV.UK AI Insights](https://www.gov.uk/government/publications/ai-insights/ai-insights-ai-coding-assistants-for-developers-in-hmg-html)
- [practice] SOX SoD is "becoming an identity-control problem" as bots and service accounts hold change permissions — [NHI Management Group on SOX SoD](https://nhimg.org/articles/sox-segregation-of-duties-is-becoming-an-identity-control-problem/) (vendor)

### Inferences
- Harness requirements: (1) one named agent identity per project or per agent slug, owned by a human owner recorded in the admin panel, with repository-scoped read/push-to-feature-branch rights and no merge/admin/deploy rights; (2) credentials injected per run, decrypted only at run start, never visible to the agent in transcripts or environment listings (placeholders), and revoked or expired at run end; (3) an access-review export (which agent identity has which rights on which repository, last used when) so the enterprise can include bots in periodic recertification; (4) model-provider keys and MCP connection credentials treated the same way; (5) every agent action attributable to the agent identity in the platform's audit log and the harness's event log.
- A GitHub App (or equivalent in GitLab/Bitbucket/Azure DevOps) is the strongest fit; where a host only offers PATs, fine-grained tokens with org-enforced maximum lifetime are the fallback and the harness should surface token expiry as a project warning.
- Rotation: enterprises will expect the harness to support credential rotation without downtime (re-read secret on next run) and to log when a secret value changed (not the value).

### Gaps
- GitHub App installation-token lifetime (60 minutes) and fine-grained PAT default/maximum lifetimes came from secondary sources only; verify in GitHub docs.
- No regulator text specific to AI-agent credentials beyond the FSB draft and OWASP; no bank policy on bot access approval found.
- GitLab/Bitbucket/Azure DevOps equivalents were not researched.

## 7. Cross-cutting: control → evidence the agent harness must record or enforce

### Takeaway
Combining the regimes, an automated agent system in a regulated enterprise must (a) preserve human roles for approval and deployment, (b) emit a complete, exportable per-change evidence record, (c) keep secrets and production/personal data out of the agent's reach and out of its transcripts, and (d) give the agent an attributable, least-privileged identity. Everything below restates findings already cited in sections 1–6; it is a synthesis, not new evidence.

### Cited Findings
- Authorised request + description + impact + testing + independent approval + fallback: DORA RTS 17(1)(a)–(h) — [Springlex](https://www.springlex.eu/en/packages/dora/rts-rmf-regulation/article-17/); PCI 6.2.3/6.2.3.1/6.5.x — [Cloudaware 6.2.3](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/06/02/03), [Cloudaware 6.5](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/06/05); SOX practice — [SafePaaS](https://www.safepaas.com/?p=11308)
- Human oversight of AI-generated code before production: NY DFS May 2026 — [Sidley](https://datamatters.sidley.com/2026/05/28/new-york-department-of-financial-services-issues-coordinated-guidance-on-frontier-ai-cybersecurity-risks/); UK GDS — [GOV.UK](https://www.gov.uk/government/publications/ai-insights/ai-insights-ai-coding-assistants-for-developers-in-hmg-html); kernel — [kernel.org](https://www.kernel.org/doc/html/latest/process/coding-assistants.html)
- Agent identity, prohibited actions, approval thresholds, audit trails: FSB draft — [TechInformed](https://techinformed.com/fsb-calls-for-tighter-controls-on-agentic-ai-in-finance/); OWASP ASI03 — [SecureFlag](https://blog.secureflag.com/2026/01/09/guide-owasp-top-ten-agentic-ai/)
- Retention horizons: PCI 12 months — [WithPCI 10.5.1](https://withpci.pages.dev/requirements/10/10.5/10.5.1); SOX auditor 7 years — [SEC](https://www.sec.gov/rules-regulations/2003/01/retention-records-relevant-audits-reviews); GitHub 180 days / Git events 7 days — [GitHub docs](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/exporting-audit-log-activity-for-your-enterprise)
- Data minimisation, storage limitation, accountability, erasure: GDPR Art. 5 and 17 — [gdpr-info Art. 5](https://gdpr-info.eu/art-5-gdpr/), [Art. 17](https://gdpr-info.eu/art-17-gdpr/); no live PANs / test data removed: PCI 6.5.5–6.5.6 — [Cloudaware 6.5](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/06/05)
- Evidence framework for auditable AI code (tool inventory, attribution, review gates, external data, reproducibility) — [CREATEQ](https://transparencywins.info/insight/createq-making-ai-generated-code-auditable-in-banking)

### Inferences (control → what the harness records or enforces)
- Authorised request: the task message from the integration layer is the request; record task id, requester/source system, timestamp, and the project config commit used. Reject tasks for projects without a valid config (already a design rule) and record the rejection reason as evidence of the intake control.
- Description and impact: require the agent to produce a structured result (summary, files touched, tests run, risks, unfinished work) via `submit_result`; store it immutably with the run.
- Tested: capture the agent's test commands and outputs in the transcript, and expose them as attachments; do not claim "tested" if no test ran — follow the kernel rule of explicit disclosure when something could not be built or tested.
- Independent approval and deployment: enforce by absence — the agent identity must have no merge/deploy rights; the harness never merges; the result event tells the integration layer where the branch/patch is. Record that the agent's push target was a feature branch named after the task id.
- Traceability: task id in branch and commit messages; trailers with run id, agent identity, model/provider, config commit, and an AI-assistance disclosure; events chain task → run → commits → result; export in a stable format (JSON) because platform logs expire.
- Reproducibility: persist model id, system-prompt/rules version, runtime image digest, project image tag (tree hash), connection list, and the config commit per run.
- Data protection: secrets only as placeholders in anything the agent or panel sees; forbid production datasets in services for scoped projects; redact PII in transcripts on ingest where feasible; documented retention schedule with automatic deletion; per-run erasure of transcript/attachments that keeps the event skeleton.
- Identity and least privilege: one owned agent identity per project, repository-scoped, short-lived credentials injected at run start; an access-review export; log every credential change (not value).
- Emergency and standard changes: no agent path that bypasses review; optional per-project allowlist of "standard change" classes an agent may complete to merge-ready state, itself a documented, approved configuration.
- AI literacy / accountability: record the human owner of each agent configuration and each project (EU AI Act Art. 4 is a staff-competence duty; the panel should make ownership explicit).

### Gaps
- Whether auditors will accept harness-generated events as "system-generated evidence" (versus screenshots/tickets) depends on the auditor's completeness-and-accuracy testing of the harness itself; no source addresses this for agent harnesses.
- No source quantifies how regulated enterprises currently treat agent transcripts in their records-management schedules.
