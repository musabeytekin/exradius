# Enterprise engineering environments and constraints for a containerised coding-agent harness

Scope: the technical environment an engineer at a large enterprise works inside, 2023–2026, and what each element implies for a harness that must clone code, build a developer image from a Dockerfile, install dependencies and run tests inside the corporate network. Prevalence figures are given with source and year; where only qualitative evidence exists this is said. "Stable" marks facts that have held for years and are unlikely to change; "moving" marks figures that drift year to year.

A note on evidence quality: almost no neutral, methodologically sound market-share data exists for enterprise developer tooling. The best available figures are (a) vendor SEC filings (JFrog, GitLab, Splunk), which are audited statements of customer counts but say nothing about competitors; (b) vendor marketing claims ("X% of the Fortune 100"), which are self-interested and often inflated relative to the same vendor's filings; (c) developer surveys (Stack Overflow, JetBrains, Docker, CNCF), which measure individual usage, not enterprise standardisation; and (d) review-site "mindshare" (PeerSpot), which measures web traffic, not deployments. Each finding below names which kind it is.

## 1. Source hosting in enterprises (GitHub Enterprise cloud/server, GitLab self-managed, Bitbucket Data Center, Azure DevOps Repos, Gerrit, Perforce) and how authentication works

### Takeaway
GitHub dominates individual developer usage and claims ~90% of the Fortune 100, but enterprises are multi-platform: GitLab claims >50% of the Fortune 100 (largely self-managed), Azure DevOps is used by ~18% of professional developers, Bitbucket is in decline after Atlassian ended Server support in February 2024 (surviving as Data Center for large on-prem shops), Perforce owns AAA games/semiconductors, and Gerrit persists in Android/telecom/embedded companies. Authentication is almost never a plain long-lived token: SAML-SSO-bound PATs, admin-enforced token lifetimes, deploy/project tokens, and SSH keys that must be SSO-authorised are the norm, so a harness needs per-host credentials whose rotation it does not control.

### Cited Findings

Prevalence (moving):
- GitHub states it is used by 90% of the Fortune 100 (vendor claim, 2025–26) — [GitHub About](https://github.com/about). The 2021 Octoverse put GitHub Enterprise at 84% of the Fortune 100 — [i-programmer summary of Octoverse 2021](https://i-programmer.info/news/136-open-source/15857-github-grows-as-business-and-open-source-establish-firm-ties.html).
- Ramp's spend data (its own customer base, so a sample of US mid-market/enterprise card spend, not the market) shows GitHub adoption at 83% of enterprises (Dec 2025) versus GitLab at 8% (May 2026) — [Ramp: GitHub](https://ramp.com/vendors/github); [Ramp: GitLab](https://ramp.com/vendors/gitlab).
- GitLab states "more than 50% of the Fortune 100 trust GitLab" (FY2026 results release; Fortune 100 defined as top 20% of the 2025 Fortune 500) — [GitLab FY2026 results, BusinessWire](https://www.businesswire.com/news/home/20260303140705/en). Its FY2025 10-K reports 1,229 customers with ARR ≥ $100k as of 31 Jan 2025 (up from 955 and 697 in the two prior years), and describes self-managed subscriptions as a distinct revenue category with one-to-three-year terms — [GitLab 10-K FY2025](https://www.sec.gov/Archives/edgar/data/1653482/000162828025014344/gtlb-20250131.htm).
- GitLab has long claimed a larger share than GitHub among organisations that host repositories on their own servers (vendor claim, older) — [InfoWorld, "Enterprise repo wars"](https://www.infoworld.com/article/3123244/enterprise-repo-wars-github-vs-gitlab-vs-bitbucket.html).
- Stack Overflow 2024 (professional developers, "Asynchronous tools"): Azure DevOps 18.3%, Jira 57.5%, Confluence 35.3%, GitHub Discussions 16.2%; Docker 58.7% — [Stack Overflow Developer Survey 2024, Technology](https://survey.stackoverflow.co/2024/technology).
- Stack Overflow 2022 (professional, version-control platforms): GitHub 55.93%, GitLab 28.9%; Bitbucket and Azure Repos below that, with "custom built solutions" at ~2.7% — [DevClass on the 2022 survey](https://devclass.com/2022/06/23/vs-code-react-git-dominant-technologies-increase-their-grip-says-stack-overflow-survey). An adesso analysis of the same survey notes GitLab, Bitbucket and Azure Repos are more likely to be used professionally than personally — [adesso blog](https://www.adesso.de/en/news/blog/stack-overflow-developer-survey-2022-part-2-2.jsp).
- JetBrains survey data (year not stated in the secondary source; likely 2021–22): GitLab rose from 33% to 38% and Bitbucket fell from 41% to 32% as a "version control service used regularly"; GitHub barely changed — [The New Stack, "I don't Git it"](https://thenewstack.io/i-dont-git-it-tracking-the-source-collaboration-market/).
- Atlassian ended support for all Server products (Jira, Confluence, Bitbucket, Bamboo, Crowd) on 15 February 2024 — [Atlassian Server end of support](https://atlassian.com/licensing/server-end-of-support). Atlassian's migration guidance steered on-premises/data-residency customers and organisations with >10,000 users to Data Center — [Atlassian key offering changes](https://www.atlassian.com/migration/key-offering-changes). GitHub built an importer for Bitbucket Server/Data Center code, PRs, comments and reviews to capture migrating customers — [GitHub Blog, Oct 2023](https://github.blog/news-insights/product-news/the-clock-is-ticking-atlassians-support-for-bitbucket-server-ends-on-february-15-2024/).
- Perforce claims Helix Core is "trusted by 19/20 top AAA game dev companies" (vendor claim); other Perforce pages say "over 90%" or "95%" of top studios and semiconductor companies, i.e. the vendor's own numbers are inconsistent — [Perforce game dev resources](https://perforce.com/resources/vcs/game-dev-resources); [Perforce Helix Core SaaS press release](https://www.perforce.com/press-releases/helix-core-SaaS-azure).
- Gerrit: Google, HTC, Qualcomm, TI and Sony Ericsson ran Gerrit by 2009 (Android ecosystem) — [LWN, 2009](https://lwn.net/Articles/359489/); a 2011 review called it "the de-facto standard for large enterprises" naming Qualcomm and SAP — [InfoQ, 2011](https://www.infoq.com/articles/learning-gerrit-code-review); the 2015 Gerrit User Summit had a talk on "Ericsson's migration to Gerrit" — [Gerrit Summit 2015 agenda](https://gerrit.googlesource.com/summit/2015/+/HEAD/sat.md). No post-2015 adoption data was found.

Authentication mechanics (stable):
- GitHub Enterprise Cloud with SAML SSO: a classic PAT must be explicitly authorised per organisation; fine-grained PATs are authorised at creation; once a user has ever authenticated via SSO for an org, only authorised PATs and SSH keys work with it even if SSO is not enforced; authorisation ends when an org/enterprise owner revokes it, the user is removed from the org, scopes are edited or the token is regenerated, or the token expires; enterprises with an IP allow list require the authorising IP to be allowed — [GitHub Docs: authorising a PAT for SAML SSO](https://docs.github.com/en/enterprise-cloud@latest/authentication/authenticating-with-saml-single-sign-on/authorizing-a-personal-access-token-for-use-with-saml-single-sign-on).
- GitHub organisation PAT policy: fine-grained PATs default to a maximum lifetime of 366 days; org policies cannot exceed the enterprise-level maximum; non-compliant tokens are blocked from the org (not revoked); classic PATs have no expiration requirement — [GitHub Docs: setting a PAT policy](https://docs.github.com/en/enterprise-server@3.17/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization).
- GitLab deploy tokens: project- or group-level username+token pairs for Git-over-HTTP, package registry and container registry; scopes `read_repository`, `read_registry`, `write_registry`, `read_package_registry`, `write_package_registry`, `read/write_virtual_registry`; no expiry by default, optional expiry date; **no SSH support**; clone form `https://<username>:<deploy_token>@gitlab.example.com/<group>/<project>.git`; group access tokens need Premium/Ultimate on GitLab.com — [GitLab Docs: deploy tokens](https://docs.gitlab.com/user/project/deploy_tokens/).
- Azure DevOps: Entra tenant administrators can enforce a maximum PAT lifespan in days across all organisations linked to the tenant (off by default), and a separate "Restrict personal access token creation" policy; Microsoft recommends combining them to drive down PAT usage — [Microsoft Learn: manage PATs with policies](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/manage-pats-with-policies-for-administrators). PAT-creation restriction entered preview June 2025 — [Azure DevOps Blog](https://devblogs.microsoft.com/devops/restricting-pat-creation-in-azure-devops-is-now-in-preview/). PATs have a hard ceiling of one year — [Microsoft Learn training module](https://learn.microsoft.com/en-us/training/modules/use-application-lifecycle/5-connect-devops-tokens).

### Inferences
- Expect at least two hosting systems per enterprise (e.g. GitHub Enterprise plus a legacy Bitbucket DC or Azure DevOps estate); a harness that assumes one host or one credential model will fail on real projects. Exradius's "one git credential per host" model matches the shape of the problem, but the credential is typically a token with a forced expiry (≤ 366 days on GitHub orgs, ≤ 1 year and often far less on Azure DevOps by policy), so credential expiry must surface as a clear, actionable error at intake rather than as a failed clone deep in a run.
- Service accounts are the realistic owner of harness credentials. On GitHub Enterprise Cloud that means a machine user or GitHub App whose PAT/installation token is SSO-authorised per org; on GitLab a deploy token (HTTPS only) or project access token; on Azure DevOps a PAT tied to a user subject to tenant lifespan policy. SSH deploy keys are viable for GitHub/Bitbucket but not GitLab deploy tokens.
- Bitbucket Data Center, Gerrit and Perforce remain in exactly the regulated, on-premises, large-codebase organisations most likely to want a self-hosted harness; Gerrit's refs/for/* push model and Perforce's non-git model mean "push a branch to origin" is not universal.

### Gaps
- No neutral 2024–2026 enterprise market-share breakdown across GitHub/GitLab/Bitbucket/Azure DevOps/Gerrit/Perforce exists in public sources; Gartner/Forrester DevOps-platform reports are paywalled. The Stack Overflow 2024 version-control-platform table could not be retrieved (page rendered without it), so the "GitHub ~87%" figure sometimes quoted for 2024 is unverified here.
- No data on the GitHub Enterprise Server (self-hosted) vs Enterprise Cloud split.
- No current (post-2015) Gerrit adoption data.

## 2. CI systems in enterprises

### Takeaway
Jenkins remains common in large organisations with legacy pipelines, while GitHub Actions and GitLab CI dominate newer work; the CD Foundation finds the best DORA outcomes among teams using both managed and self-hosted CI, which is the typical enterprise mix.

### Cited Findings
- CD Foundation / SlashData State of CI/CD 2024: 83% of developers are involved in DevOps activities; CI/CD tool use correlates with better performance on all DORA metrics, strongest for developers using both managed and self-hosted tools; data pooled from six Developer Nation surveys (Q3 2020–Q1 2023, >125,000 respondents) — [CD Foundation State of CI/CD 2024](https://cd.foundation/state-of-cicd-2024/).
- JetBrains State of Developer Ecosystem 2025 (as relayed by a secondary source; options not mutually exclusive): organisational use of GitHub Actions 33%, Jenkins 28%, GitLab CI 19% — [Quash, CI/CD statistics](https://quashbugs.com/blog/ci-cd-statistics). Secondary; the JetBrains 2025 report page itself was not retrieved with these numbers.

### Inferences
- A harness is not a CI system, but it will run inside the same network as self-hosted Jenkins/GitLab runners and will need the same egress (mirrors, registries) those runners already have; the fastest path to a working Dockerfile is often to copy what the CI runner image does.

### Gaps
- Tool-level percentages from the CD Foundation 2024 report itself were not in the retrievable text.

## 3. Package and artifact mirrors (Nexus, Artifactory, Azure Artifacts, GitHub Packages); how builds are pointed at them; blocked public registries

### Takeaway
A private artifact manager is near-universal in large enterprises: JFrog's audited filings put Artifactory at 83% of the Fortune 100 (2025) and Sonatype claims 70%; the two together are the market. Builds are pointed at them through per-tool config files (Maven `settings.xml` `<mirrorOf>*</mirrorOf>`, `.npmrc` `registry=`, `pip.conf` `index-url`, `GOPROXY`), and the realistic default inside a bank or insurer is that `repo1.maven.org`, `registry.npmjs.org`, `pypi.org` and `proxy.golang.org` are unreachable from build hosts.

### Cited Findings

Prevalence (moving):
- JFrog's FY2025 annual report: ~6,600 customer organisations including approximately 83% of Fortune 100 organisations as of 31 Dec 2025 (82% a year earlier) — [JFrog ARS FY2025 (SEC)](https://www.sec.gov/Archives/edgar/data/1800667/000119312526145590/frog_2026_ars.pdf); [JFrog ARS FY2024 (SEC)](https://www.sec.gov/Archives/edgar/data/1800667/000095017025051595/frog_2025_ars.pdf). JFrog marketing says "nearly 90%" / "89 of the Fortune 100", higher than the filing — [JFrog customer stories](https://jfrog.com/ebook/enterprise-devsecops-artifact-management-jfrog-stories/).
- Sonatype claims "more than 70% of the Fortune 100", 15 million developers and ~2,000 organisations (vendor claims, 2025) — [Sonatype Nexus Repository quote page](https://www.sonatype.com/products/sonatype-nexus-repository/quote); [Sonatype Nexus Repository Cloud launch, Oct 2025](https://business.mammothtimes.com/mammothtimes/article/gnwcq-2025-10-8-sonatype-launches-nexus-repository-cloud-for-the-gen-ai-era). An earlier Nexus release claimed >100,000 active installations — [Sonatype Nexus 3 press release](https://www.sonatype.com/press-releases/nexus-3-press-release).
- PeerSpot "mindshare" (web engagement, not deployments): Artifactory ~37%, Nexus ~33% of the repository-manager category — [PeerSpot repository managers leaderboard](https://www.peerspot.com/categories/repository-managers/leaderboard).
- Sonatype's 10th State of the Software Supply Chain (Oct 2024): 6.6 trillion open-source downloads in the year; 156% year-over-year surge in open-source malware; data from >7 million projects — [Sonatype press release](https://www.sonatype.com/press-releases/sonatypes-10th-annual-state-of-the-software-supply-chain-report). This is the stated rationale for enterprises forcing all dependency traffic through a proxying repository with policy ("firewall") rules.

Mechanics (stable):
- Maven: mirrors are declared in `${user.home}/.m2/settings.xml` (or the global `${maven.home}/conf/settings.xml`); `<mirrorOf>*</mirrorOf>` routes every repository request, including ones declared in project POMs, through one URL and "is typically used with an internal repository manager"; `external:*` excludes localhost/file repos; `external:http:*` (Maven 3.8+) catches plain-HTTP repos; Maven does not aggregate mirrors, the first match wins; mirror config belongs in settings, not the POM — [Maven: Guide to Mirror Settings](https://maven.apache.org/guides/mini/guide-mirror-settings.html).
- npm: `registry` defaults to `https://registry.npmjs.org/`; scoped registries via `--scope=@mycorp --registry=...` (persisted as `@mycorp:registry=` in `.npmrc`); per-registry auth as `//other-registry.tld/:_auth`; `ca`/`cafile` for custom CAs; `strict-ssl` defaults true; `proxy`/`https-proxy` honour `HTTP(S)_PROXY`, `noproxy` honours `NO_PROXY`; `.npmrc` is read per-project, per-user (`~/.npmrc`), global (`$PREFIX/etc/npmrc`) and built-in; precedence CLI > env > npmrc > defaults — [npm Docs: config](https://docs.npmjs.com/cli/v10/using-npm/config).
- pip: config files at `/etc/pip.conf` and `/etc/xdg/pip/pip.conf` (global), `~/.config/pip/pip.conf` (user; legacy `~/.pip/pip.conf`), `$VIRTUAL_ENV/pip.conf` (site); `PIP_CONFIG_FILE` overrides; any option is settable as `PIP_<UPPER_NAME>` (e.g. `PIP_INDEX_URL`, `PIP_TRUSTED_HOST`); `pip config debug` shows the resolved paths — [pip: Configuration](https://pip.pypa.io/en/stable/topics/configuration/).
- Go: `GOPROXY` is a comma-separated list of proxy URLs plus `direct`/`off`; with `GOPROXY=https://corp.example.com,https://proxy.golang.org` the second is tried only on 404/410 from the first; `GOPRIVATE`/`GONOPROXY` control which module paths bypass the proxy; `GOINSECURE` replaces the deprecated `-insecure` flag; `go.sum` records checksums — [Go Modules Reference](https://go.dev/ref/mod#private-modules). (The reference's environment-variable section was not retrieved; defaults `GOPROXY=https://proxy.golang.org,direct` and `GOSUMDB=sum.golang.org` are general knowledge and should be verified there.)
- Air gap: JFrog documents exporting signed Release Bundles to removable media and importing into an isolated Artifactory, "mainly intended for organizations such as financial institutions and military installations" with no network path between instances; requires Enterprise+ licence — [JFrog Docs: air gap distribution (v1)](https://docs.jfrog.com/artifactory/docs/distribute-release-bundles-v1-in-an-air-gap-environment). A DMZ Artifactory that downloads public dependencies, exports them and an internal instance that imports is the lower-level pattern — [JFrog Blog: Artifactory with an air gap](https://jfrog.com/blog/using-artifactory-with-an-air-gap/).

### Inferences
- The workstation image and the run environment must be able to carry per-ecosystem mirror configuration that the harness injects, not the project's committed files: `~/.m2/settings.xml`, `~/.npmrc`, `~/.config/pip/pip.conf`, `GOPROXY`/`GOPRIVATE`/`GONOSUMDB`, `NUGET.config`, plus registry credentials. Because these are per-host (not per-project) facts, they belong at the admin layer alongside git credentials; Exradius's `env` and service settings can carry them today but a first-class "mirror profile" would reduce per-project repetition.
- `GOSUMDB`/`GOPRIVATE` is the one place where a mirror alone is not enough: private module paths must also be excluded from the public checksum database or `go` will try to reach `sum.golang.org`.
- Dockerfile `RUN` steps that install packages at build time hit the same walls as the agent's later `npm install`; the build must receive the same mirror config and CA bundle as the run (BuildKit secrets or build args), or images that build on a laptop will fail on the worker.
- In fully air-gapped zones a harness cannot pull anything at run time; the only workable model is "everything comes from the internal Artifactory/Nexus", including the runtime bundle and base images.

### Gaps
- No prevalence data for Azure Artifacts or GitHub Packages as the primary enterprise mirror; both appear only as adjuncts in the sources found.
- No survey quantifying how many enterprises block direct access to public registries; the evidence is the near-universal presence of proxying repository managers plus vendor air-gap documentation.

## 4. Container registries and base images (Harbor, Artifactory, ECR, ACR), golden/hardened base images, scanning gates, rules against Docker Hub

### Takeaway
Large enterprises pull from a private registry (Artifactory, Harbor, ACR/ECR) with a curated, periodically rebuilt set of approved base images and admission policies that reject other registries; Docker Hub is throttled (100 anonymous pulls per 6 hours per IP) and commonly blocked or proxied. Vendor images for Oracle and IBM products are not on Docker Hub at all: they require a login and licence acceptance at the vendor's registry.

### Cited Findings
- Docker Hub pull limits (current docs page): unauthenticated 100 pulls per 6 hours per IPv4 address or IPv6 /64; authenticated Personal 200 per 6 hours; Pro/Team/Business unlimited subject to fair use; two distinct 429 responses (abuse rate limit vs pull limit) — [Docker Docs: Docker Hub usage and limits](https://docs.docker.com/docker-hub/usage/). Docker's docs repository earlier proposed stricter limits ("10 pulls/hour per IP unauthenticated, 40/hour authenticated free", for 1 March or 1 April 2025) — [docker/docs PR #21494](https://github.com/docker/docs/pull/21494/files); [GitLab issue tracking the change](https://gitlab.com/gitlab-org/gitlab/-/issues/526605). The two sources conflict; the live docs page should be treated as authoritative at any given time. Sonatype publishes guidance on handling Docker Hub 429s via a Nexus proxy — [Sonatype KB](https://support.sonatype.com/hc/en-us/articles/33993902899731-Handling-request-rate-limiting-from-Docker-Hub).
- Microsoft's Zero Trust DevSecOps guidance: free choice of public base images is a supply-chain risk; recommends a curated set of verified base images hosted in a private registry (e.g. ACR), rebuilt on a schedule, with Azure Policy "allowed registries" admission control and Defender for Containers gated deployment to deny non-compliant images — [Microsoft Zero Trust Assessment DS_082](https://microsoft.github.io/zerotrustassessment/docs/workshop-guidance/devsecops/DS_082).
- US DoD Iron Bank (Platform One): hardened images at `registry1.dso.mil`; no anonymous pulls; images hardened to DoD benchmarks and scanned with OpenSCAP, Twistlock (Prisma) and Anchore; accredited containers carry DoD-wide reciprocity; max image size 20 GB — [Iron Bank FAQ](https://docs-ironbank.dso.mil/faq/); [Microsoft Azure Government blog on SQL Server in Iron Bank](https://devblogs.microsoft.com/azuregov/sql-server-2019-on-rhel8-container-now-available-on-iron-bank-dods-centralized-artifacts-repository/).
- Oracle Container Registry: database images require signing in, accepting the licence agreement, then `docker login` with Oracle SSO credentials (or an auth token); only images containing solely open-source software can be pulled anonymously — [Oracle docs: Setting Up Oracle Database (containers)](https://docs.oracle.com/cd/G30558_01/books/DeployCont/c-Setting-Up-Oracle-Database.html); [Oracle Linux blog](https://blogs.oracle.com/linux/easier-access-to-open-source-images-on-oracle-container-registry).
- IBM MQ: the developer image moved from Docker Hub (deprecated, no further updates) to `icr.io/ibm-messaging/mq`; running it requires `LICENSE=accept` — [IBM Docs: MQ developer container image](https://www.ibm.com/docs/en/SSFKSJ_9.3.0/container/developers-container-image.html).
- Scanning adoption: the only survey with numbers found is AWS's 2020 container security survey, where the share of respondents not scanning images fell from 83% to 70%, with Prisma Cloud and Aqua "gaining traction" — [AWS Containers Blog, 2020](https://aws.amazon.com/blogs/containers/results-of-the-2020-aws-container-security-survey). Trivy (Aqua's OSS scanner) is embedded in GitLab, Harbor and other platforms — [Aqua press release](https://www.aquasec.com/news/trivy-vulnerability-scanner-aqua-security-adopted-by-leading-cloud-native-platforms). PeerSpot 2026 mindshare for container security: Wiz 9.7%, Prisma Cloud 8.0%, Trivy 3.4%, "Other" 78.9% (web engagement, weak) — [PeerSpot Trivy](https://www.peerspot.com/products/trivy/questions).
- CNCF 2024 survey: 750 respondents; 89% cloud-native adoption; a secondary report says 82% of container users run Kubernetes in production (unverified against the PDF) — [CNCF Annual Survey 2024](https://www.cncf.io/reports/cncf-annual-survey-2024/). Harbor is a CNCF graduated registry with ongoing production adoption but no per-project percentage was found — [Harbor adopters list](https://git.lipovcan.cz/Upstream/harbor/raw/branch/main/ADOPTERS.md).

### Inferences
- `FROM ubuntu:24.04` in a project Dockerfile will fail or be rejected inside many enterprises; the harness must let the workstation `FROM` line (and the harness's own `exradius-project-default` and `exradius-runtime-claude-code` images) be re-based onto the company's golden image or pulled through the internal registry proxy. The runtime-bundle design (relocatable Python + Claude Code binary mounted read-only into any glibc image) fits this: the company's golden image can be the workstation, as long as the bundle itself can be delivered via the internal registry or Artifactory rather than Docker Hub.
- Where image scanning is a gate (Prisma/Aqua/Trivy policy in Harbor or Artifactory Xray), a workstation image the harness builds locally and never pushes bypasses the gate, which security teams may object to; building through the company's registry so the image gets scanned is the compliant path, at the cost of slower runs.
- Vendor developer images (Oracle Free, Db2 CE, IBM MQ) need registry credentials and licence acceptance; a project `services:` entry that references `container-registry.oracle.com/database/free` needs a registry credential the admin owns, not the project.

### Gaps
- No 2023–2026 survey quantifying enterprise use of Harbor vs Artifactory vs ECR/ACR as the primary registry, nor the share of enterprises that block Docker Hub outright.
- No neutral adoption figure for image-scanning gates by vendor after 2020.

## 5. Network: authenticated outbound proxies, TLS inspection and corporate CA certificates, air-gapped/restricted zones, VPN-only internal services

### Takeaway
Enterprise egress is typically via an explicit or transparent proxy that may require NTLM/Kerberos authentication and that re-signs TLS with a corporate root CA; every container (build stage and run stage) must trust that CA at the OS level and in each language runtime's own trust store (Java cacerts, Node `NODE_EXTRA_CA_CERTS`, Python `REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE`, pip `cert`, npm `cafile`), and must receive `HTTP(S)_PROXY`/`NO_PROXY`. Internal hosts are often reachable only from inside the VPN/zero-trust perimeter, so the worker's network position, not the agent's, decides what is reachable.

### Cited Findings
- Zscaler ThreatLabz 2024: 87.2% of blocked attacks were delivered over encrypted channels (32.1 billion encrypted attacks, Oct 2023–Sep 2024); the report's main recommendation is TLS/SSL inspection "at scale", inspecting 100% of traffic (vendor telemetry) — [Zscaler ThreatLabz blog](https://www.zscaler.com/blogs/security-research/threatlabz-report-threats-delivered-over-encrypted-channels).
- Older neutral-ish surveys on how many enterprises actually decrypt: IDC for F5 (2016) found only 25% decrypt and inspect inbound and outbound traffic though 90% said encryption diminished visibility — [F5/IDC "Blind State of Rising SSL Traffic"](https://uk-qae.insight.com/content/dam/insight-web/emea/partner/f5/F5_IDC_Report_The%20Blind%20State%20of%20Rising%20SSL%20Traffic.pdf); Ponemon for A10: 61% cite performance as the biggest barrier, 57% consider inspection essential/very important — [Ponemon/A10 report](https://www.ponemon.org/local/upload/file/A10%20Report%20Final.pdf); ESG for Broadcom: only 20% take a strategic approach to decryption — [ESG report via Broadcom](https://docs.broadcom.com/doc/esg-report-network-encryption-and-its-impact-on-network-security). These are dated (2016–2018) and vendor-sponsored.
- Mechanics of TLS-inspecting proxies and Docker: the proxy terminates TLS and re-issues certificates from an enterprise root; builds fail with `x509: certificate signed by unknown authority` until the CA is trusted; trust must be set at three layers (host, Docker daemon for pulls, build-time containers for `apt`/`curl`/package managers); the Dockerfile pattern is copy the CA into `/usr/local/share/ca-certificates/` and run `update-ca-certificates` after installing `ca-certificates`; Python needs `REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE`; proxies are passed as build args and internal hosts go in `NO_PROXY` — [Ansys: Docker with TLS-inspecting proxy servers](https://ansyshelp.ansys.com/public/Views/Secured/hpcplat/v140/en/hps_dg/docker_tls_proxy_servers.html); [OneUptime: Docker proxy settings for corporate environments](https://oneuptime.com/blog/post/2026-01-16-docker-proxy-settings-corporate/markdown); [ddev networking docs](https://docs.ddev.com/en/stable/users/usage/networking/); [Pants user report of x509 failure behind transparent proxy](https://chat.pantsbuild.org/t/22885795/i-am-using-pants-behind-a-transparent-corporate-proxy-that-d).
- A documented "build contract" for Node-based agent images: pass the CA as a build argument, install each certificate as an OS trust anchor, and set `NODE_EXTRA_CA_CERTS` before dependency checks — [NVIDIA NemoClaw: configure corporate CA trust](https://nvidia-preview-pr-8588.docs.buildwithfern.com/nemoclaw/user-guide/openclaw/security/configure-corporate-ca-trust). Node documents `NODE_EXTRA_CA_CERTS=file`, `NODE_TLS_REJECT_UNAUTHORIZED`, `--use-openssl-ca`, `--use-system-ca` and `NODE_USE_SYSTEM_CA=1` — [Node.js CLI docs](https://nodejs.org/api/cli.html#node_extra_ca_certsfile) (section bodies not retrieved; anchors confirmed).
- Java: "PKIX path building failed" is the symptom of a corporate CA missing from the JDK truststore; fix is `keytool -importcert -trustcacerts` into `$JAVA_HOME/lib/security/cacerts` (default password `changeit`) and bake it into the image, since certificates imported at runtime vanish on restart — [Dependency-Track: internal CA](https://docs.dependencytrack.org/getting-started/internal-ca/); [NTT Data technical article](https://ca.nttdata.com/en/insights/technical-articles/2020/september/install-certificates-to-resolve-pkix-issue).
- Authenticating proxies: Px is an HTTP(S) proxy that authenticates to NTLM or Kerberos upstream proxies and ships as a Docker image (needs `--gateway` mode when publishing a port) — [px-proxy on PyPI](https://pypi.org/project/px-proxy); Cntlm handles NTLM only, is a SourceForge binary "not updated in over five years" and will not work with Kerberos-only proxies — [Docker forums thread](https://forums.docker.com/t/proxy-server-domain-authentication/25446); Docker Desktop 4.30 added native SOCKS5, NTLM and Kerberos proxy support, replacing basic-auth-only — [Docker blog](https://www.docker.com/blog/navigating-proxy-servers-docker-desktop-4-30/).
- Air gap: see §3 (JFrog Release Bundles via removable media; financial institutions and military installations).

### Inferences
- The corporate CA bundle is a per-installation fact, not per-project: the harness should install it once (worker host, Docker daemon, build args for every image build, and a bind mount or env in every run container) and set the language-runtime variables (`SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS`, `PIP_CERT`, npm `cafile`, Java `-Djavax.net.ssl.trustStore` or a patched cacerts) so the agent's `pip install`/`npm install`/`mvn` work without each project repeating the recipe.
- The Claude Agent SDK/Claude Code binary inside the run container also makes outbound TLS calls (to the model provider or an internal gateway); it is subject to the same inspection and proxy, so the runtime bundle itself must honour `HTTPS_PROXY` and the CA env vars, and the "environment stripping" in the runner must not strip them.
- `NO_PROXY` must include the internal API alias (`exradius-api`), the per-run service names, and internal git/artifact hosts, or the proxy will swallow intra-run traffic.
- Where the upstream proxy demands NTLM/Kerberos from a human identity, a harness has no identity to offer; the practical answers are a service-account proxy credential, a proxy exemption for the worker subnet, or an intermediate like Px. This is an installation prerequisite to document, not something a project config can solve.

### Gaps
- No current (2023–2026) neutral figure for the share of enterprises performing TLS inspection on developer/build egress; only vendor telemetry and 2016–2018 surveys.
- No data on how common authenticating (NTLM/Kerberos) proxies are versus IP-allow-listed transparent proxies for server subnets.

## 6. Secrets management: Vault, CyberArk, cloud secret managers; short-lived credentials; policies against long-lived tokens

### Takeaway
HashiCorp Vault is the share leader in stand-alone secrets management (Gartner via trade press, 2024) with CyberArk the main enterprise rival; the direction of policy everywhere is short-lived, leased, auto-revoked credentials, while the measured reality is 23.8–29 million new hardcoded secrets per year in public GitHub alone and 70% of 2022 leaks still valid, which is why enterprises push back on any tool that holds plaintext long-lived tokens.

### Cited Findings
- "Gartner said HashiCorp has the highest market share for stand-alone secrets management"; CyberArk and HashiCorp "go toe-to-toe" on capabilities and pricing (April 2024, around IBM's HashiCorp acquisition) — [BankInfoSecurity](https://www.bankinfosecurity.com/blogs/what-ibm-purchasing-hashicorp-means-for-secrets-management-p-3618).
- PeerSpot mindshare (web engagement, June 2026): HashiCorp Vault 6.8% vs CyberArk Secrets Management 2.1% in "Secrets Management Tools" — [PeerSpot comparison](https://www.peerspot.com/products/comparisons/cyberark-identity_vs_hashicorp-vault).
- Vault lease model (stable): every dynamic secret and service token has a lease with a TTL and renewability; Vault auto-revokes at expiry; consumers must renew within the TTL or fetch a replacement; revocation (API, CLI, UI, or automatic) invalidates immediately; prefix revocation can revoke e.g. all `aws/` credentials; the KV engine does not issue leases — [Vault Docs: Lease, renew, and revoke](https://developer.hashicorp.com/vault/docs/concepts/lease).
- GitGuardian State of Secrets Sprawl 2025 (covering 2024): ~23.8 million new hardcoded secrets in public GitHub commits (+25% YoY); generic secrets (passwords, DB connection strings, custom tokens) 58% of detections (up from 49%); 35% of private repositories contain hardcoded secrets; 70% of secrets leaked in 2022 remain active — [GitGuardian blog](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2025/); [InfoQ summary](https://www.infoq.com/news/2025/03/gitguardian-secret-sprawl-report). The 2026 edition (covering 2025): 29 million new secrets (+34%); 28% of incidents originated outside source code (Slack, Jira, Confluence) — [The Hacker News on the 2026 report](https://thehackernews.com/2026/03/the-state-of-secrets-sprawl-2026-9.html).
- Platform-enforced token lifetimes (see §1): GitHub org default 366-day maximum for fine-grained PATs; Azure DevOps tenant-wide maximum lifespan policy and PAT-creation restriction — [GitHub Docs](https://docs.github.com/en/enterprise-server@3.17/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization); [Microsoft Learn](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/manage-pats-with-policies-for-administrators).

### Inferences
- An enterprise security review will ask where the harness's secrets live and how they rotate. Exradius's encrypted-at-rest store with write-only API and `${secret:NAME}` indirection answers "where"; it does not answer "how do they rotate", and enterprises with Vault will want the store to be Vault (or CyberArk Conjur / AWS Secrets Manager) rather than a local Fernet store. A pluggable secret-store backend that fetches at run start (matching the existing "decrypt only in resolve.py at run start" design) is the natural fit, and Vault's lease model means a run longer than the lease must renew or re-fetch.
- The 70%-still-active statistic is why reviewers care about transcripts and logs: Exradius's `$NAME` placeholder discipline in everything shown to the panel, the agent and the events is exactly what such a review checks, and it should extend to anything the agent echoes (e.g. `env` output) — a transcript scrubber keyed on known secret values is a cheap safeguard.
- Git credentials for the harness are themselves long-lived tokens by enterprise definition; expect pressure to use GitHub App installation tokens (1-hour) or Vault-issued dynamic credentials rather than a stored PAT.

### Gaps
- No 2024–2026 revenue-based market shares for Vault vs CyberArk vs AWS/Azure/GCP secret managers; Gartner's number is relayed secondhand without a figure.
- No survey on how many enterprises prohibit long-lived tokens for service accounts; the evidence is platform policy features and the secrets-sprawl numbers that motivate them.

## 7. Observability and logs: Splunk, Elastic/OpenSearch, Dynatrace, AppDynamics, Datadog, Grafana/Loki, New Relic; how engineers query them; access control

### Takeaway
Splunk (>90 of the Fortune 100 per its last 10-K before Cisco's acquisition), Datadog, Dynatrace, New Relic, Elastic and Grafana are the 2024 Gartner leaders; engineers query via web UI and saved searches, and via REST APIs (Splunk on management port 8089) that are gated by role-based index restrictions and search capabilities, with no way to stop export for anyone who can search. Logs are the data most likely to contain PII and the most tightly access-controlled, so agent access to them is usually read-only, index-scoped, and via a service identity.

### Cited Findings
- Gartner Magic Quadrant for Observability Platforms 2024 leaders: Datadog, Dynatrace, New Relic, Elastic, Splunk, Grafana Labs, Chronosphere; Gartner noted Cisco's Splunk integration was "a work in progress" — [Channel Futures on the 2024 MQ](https://channelfutures.com/security/gartner-magic-quadrant-observability-platform-leaders).
- Splunk FY2020 10-K: >19,400 customers in >130 countries including over 90 of the Fortune 100 as of 31 Jan 2020 (last standalone figure found; Splunk was acquired by Cisco in 2024) — [Splunk 10-K FY2020 (SEC)](https://www.sec.gov/Archives/edgar/data/1353283/000135328320000008/a01312010k.htm).
- Splunk access control (practitioner answers on Splunk Community; stable semantics): roles restrict which indexes and events a user can search; roles cannot hide individual fields within an event (workarounds: summary indexes or dashboards with "Open in search" disabled); "if they can search then Splunk doesn't have any control to stop them from exporting" via REST/CLI; `export_results_is_visible` only hides the Web export button; the REST API shares management port 8089 — [Splunk Community: restrict export via REST/CLI](https://community.splunk.com/t5/Splunk-Enterprise/How-to-restrict-users-from-export-data-via-RestAPI-CLI/m-p/591681/highlight/true); [Splunk Community: user permissions](https://community.splunk.com/t5/Security/Splunk-User-Permissions-Is-it-possible-to-restrict-at-this-level/m-p/619615).
- Market-size framing: Gartner's June 2024 Invest note covers Datadog, Dynatrace and Cisco/Splunk dynamics but is paywalled — [Gartner document 5486095](https://www.gartner.com/en/documents/5486095).

### Inferences
- An MCP connection to logs (Exradius catalog) must carry a service identity scoped to the project's indexes; enterprises will not hand an agent a human's Splunk session. Because export cannot be blocked for a searching identity, the only real control is the index/role scope, so the harness should surface exactly which indexes/roles a connection has (as it does for non-secret settings) and treat log query results as potentially containing PII in transcripts.
- Observability tools are reached only from inside the network (Splunk on 8089, Dynatrace/AppDynamics on-prem controllers), another reason the run container's network position (joins the run network, resolves internal hosts through the proxy/VPN) is a prerequisite.

### Gaps
- No 2024–2026 vendor market-share percentages for observability (Gartner Market Share is paywalled); only the leaders list.
- No data on how enterprises expose logs to automation (API tokens vs SSO-only); the Splunk mechanics above are the only concrete evidence found.

## Cross-cutting implications checklist for a Dockerfile-building, test-running harness inside the corporate network

Derived from the findings above; each line is an inference, not a cited fact.

1. **Installation-level, not project-level, prerequisites:** corporate root CA bundle; `HTTP(S)_PROXY`/`NO_PROXY` (with the internal API alias and run-network service names in `NO_PROXY`); proxy service credential or subnet exemption if the proxy authenticates; internal registry mirror for the harness's own images and runtime bundle; per-host git credentials with known expiry; per-ecosystem mirror configuration (`settings.xml`, `.npmrc`, `pip.conf`, `GOPROXY`/`GOPRIVATE`, `NuGet.config`); registry credentials for vendor developer images.
2. **Build and run must see the same network configuration:** image builds (`RUN apt-get`, `RUN npm ci`) need the CA and proxy as build args/secrets exactly as the run container does, or images that build on a laptop fail on the worker.
3. **Credential expiry is routine:** surface expired/unauthorised tokens (SSO not authorised, lifetime policy exceeded) as intake-time diagnostics with the platform's own wording.
4. **Base image re-basing:** allow the workstation and harness images to be built `FROM` the company's golden image or pulled through its registry; expect image-scan gates and plan for building through the registry when required.
5. **Services are heavy and licensed:** Oracle Free (2 GB RAM, 12 GB data), Db2 CE (up to 16 GB), SQL Server Developer, IBM MQ Developer need licence-acceptance env vars, registry logins, start-up health checks and per-run memory budgeting; the mainframe and TIBCO are out of reach without licensed emulators or shared instances.
6. **Secrets posture will be audited:** pluggable store (Vault/CyberArk/cloud) with lease-aware fetch at run start; placeholder discipline extended to transcript scrubbing; prefer short-lived app tokens over stored PATs where the platform offers them.
7. **Test results need context:** preserve raw output, distinguish "could not run" from "failed", and expect a few percent of runs to fail for reasons unrelated to the change.
8. **Caches are the main performance lever** for multi-module builds, and must be per-project to avoid leaking private artifacts between tenants.
